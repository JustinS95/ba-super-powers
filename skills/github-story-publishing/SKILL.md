# GitHub Story Publishing

Publish a bounded reviewed story set as repository **Issues**, then add those Issues to one selected existing Project. Not draft issues, a full sync engine, or permission to update existing Issue text. Existing mapped Issues may be verified and added; they must not be recreated.

## Inputs and contracts

Read [COMMON](../../references/COMMON.md), relevant adopted [PROJECT_CONTEXT](../../references/PROJECT_CONTEXT.md), [GITHUB_MUTATIONS](../../references/GITHUB_MUTATIONS.md), and [github-operations](../github-operations/SKILL.md). Require selected reviewed source paths/keys/versions, exact repository and owner-scoped Project, approved connection/actions, exact title/body transformation, privacy decision, bounded duplicate/recovery reads, and approved durable run paths. Optional: initial **existing** labels, exact Status mapping, stable publication marker, separately approved existing-schema local mapping writeback.

Ask when content authority, source identity, target/visibility, recovery method, duplicate mapping, required data or schema is unknown. No inferred UUID, repository from working directory, automatic Task/Feature hierarchy, or business-rule invention. If required inputs are missing, explain the gaps in chat and stop before making changes.

## Workflow

1. **Read only selected sources.** Preserve approved behavior and testable AC/provenance. Inventory stable source keys separately from paths/titles and remote identity tuples; check duplicate source keys/mappings and prior manifests. A Git-new file or missing remote mapping is only a create candidate. If requirements need revision, return questions/proposed content; do not silently improve it while publishing.
2. **Resolve target/access and collisions.** Discover schemas and current repository/Project IDs, visibility, permissions, Issue support, field/options if used, and known automation effects. Verify any mapped Issue's host/repo/node ID/number/URL against source/provenance. Contradictions stop. Compare existing mapped content without updating it; content drift blocks claims that current source was published. Without mapping, use approved marker/prior run evidence plus bounded complete open/closed repository reads; title similarity is only a hint. Unresolved identity blocks create.
3. **Prepare exact content and privacy gate.** Show final string title and raw Markdown body including all AC, approved links and any stable marker. No implicit internal source path, personal data, mention, attachment, task creation or hierarchy link. A hypothetical marker such as `<!-- publication-key: demo-story-17 -->` is visible in raw body and needs explicit approval/uniqueness checking; do not invent or insert it silently. Verify public repository and Project separately, review all public content/metadata/links/markers, and obtain explicit publication approval. Omit labels by default; otherwise discover and approve existing exact repository labels, never create new ones. Do not copy local metadata wholesale.
4. **Review staged immutable manifest.** Use [run records](../github-operations/run-records.md). Include one create where needed, one add per Issue, optional exact Status, optional local writeback; list all no-actions. Approve exact payloads/hashes, targets, initial Status baseline rule and race risk, source hashes, recovery reads/retry limits and typed Issue-ID/item-ID bindings. Without approved binding rules, stop for separate resolved-payload review between stages. COMMON requires explicit durable manifest/results paths and collision/retention decisions before mutations; never store operational records in an assumed temp folder.
5. **Create, verify, then add.** Recheck authority/visibility/source hash before publication. Record attempt before create, verify returned Issue identity and exact material via re-read, persist results/bindings. Issue creation and Project addition are separate calls. Before add, immediately compare protected Issue state/content/approved labels with approved baselines; include known automation effects and permitted initial/relevant Project field values in the plan. Known effects outside this MVP block add pending a separately scoped decision. Add only the verified intended Issue to the selected Project; re-fetch item membership/content identity plus protected Issue values and relevant Project fields, and checkpoint its separate item ID. Unexpected changes are discrepancies: report observed membership separately and stop dependent mutations pending review, without assuming causality, reverting, or disabling automation. Existing membership can be verified/reused with the same protected-value checks; do not add drafts or select by title. Verify optional labels because the Issue endpoint can silently drop them without sufficient permission.
6. **Optional Status boundary.** Hand the unchanged approved operation/bindings to [github-project-board](../github-project-board/SKILL.md); no automatic mapping from Issue state or label. If Project automation has changed the expected initial Status, stop for rebase approval. Partial add/Status failure leaves the verified Issue intact; never delete/recreate it.
7. **Optional local identity writeback.** Only after verified identities are durably recorded, show/apply the separately approved diff to the selected existing canonical schema with unchanged source baseline. Preserve local identity/relationships and unrelated content; no invented frontmatter keys, migration or shadow story store. Re-read exact source key and remote tuple. If no adopted mapping schema exists, retain identities in the run record and ask; this does not force configuration creation. Failure is partial: resume writeback, not create.
8. **Reconcile and finish.** Timeout/interruption follows GITHUB_MUTATIONS: marker/material/scope reconciliation before any retry, complete bounded reads, stop on multiple/zero-inconclusive matches. Reverify saved identities on resume. Return per-story operation outcomes and remaining decisions, not a blanket “published” when only Issues exist.

## Outputs and checks

No-write publication table/exact payload review; after authorized execution, manifest/checkpoints, one-to-one source-to-Issue and Issue-to-Project-item mapping, optional Status/writeback results, missing/unexpected/duplicate identities, content differences, verification timestamps/completeness and actual retained paths/actions. Canonical content is unchanged unless the separate writeback is approved. [Scenarios](scenarios.md) cover happy, privacy, conflict and recovery paths.

MVP excludes Issue title/body edits, comments, assignments, estimates, Issue types/fields, sub-issues/dependency automation, state changes, Project/field creation, visibility changes, archive/delete and bidirectional sync. Do not send excluded fields even if the API supports them.
