# GitHub transport, publication, and recovery contract

Read with [COMMON](COMMON.md) and relevant adopted [PROJECT_CONTEXT](PROJECT_CONTEXT.md). This contract covers modern GitHub Projects (ProjectV2), not Projects classic or ADO. These are reusable instructions, not authorization to connect or publish.

## Capability, authority, and identity

- Discover available approved integrations and their actual schemas. Prefer an authorized existing connection. CLI/REST/GraphQL are alternatives only when available and explicitly authorized; never assume `gh`, shell access, credentials, or an MCP capability exists. Missing capability yields a no-write plan/export request, not installation or guessed calls.
- Bind every run to exact host, authenticated principal/connection, repository owner/name and node ID, and Project owner kind (user/organization), login/node ID, number/node ID/URL. A Project is owner-scoped, not a repository board. Resolve actual repository and Project visibility independently. Stop on account/host/target change; no silent fallback or cross-host redirects.
- GitHub identity uses verified host + exact login and account node ID/provenance, or the documented authenticated App/installation identity. Display names are hints, not identity; do not guess email, derive GUIDs, or apply ADO email/GUID resolution. Identity evidence does not confer business authority.
- Verify permissions separately for repository Issue creation/reads and Project reads/writes. The API guide describes `read:project` for read queries and `project` for mutations with classic tokens; the CLI manual documents `project` for `gh project`. App/fine-grained credentials and enterprise hosts need their own current permission/support verification. Do not prescribe token creation, expand scopes, log in, inspect credential files, or print secrets as an automatic prerequisite. Request authorized access through secure host mechanisms when absent.
- Verify current operation documentation and host support before constructing requests. Serialize source text as data/variables, never executable interpolation. Check HTTP/transport status **and GraphQL errors/partial data**, including successful HTTP responses. Retain sanitized evidence, not tokens, headers, or secret fingerprints.

## Objects and bounded reads

Keep distinct: local source key/identity and path/version; host/repository/Issue node ID/number/URL; owner/Project node ID/number; Project-item node ID; field ID/type and single-select option ID/name. No UUID requirement or incidental canonical schema migration. Repository Issue state (`open`/`closed`) is not Project Status; setting Status does not authorize closing an Issue.

Bound reads by approved targets, selected IDs or declared query and time window. Paginate every relevant connection, including nested fields/field values, using documented cursors or REST links. CLI default limits and first-page examples are not complete snapshots. Record pages/cursors, collection time, scope, expected/returned/missing/duplicate identities, errors, truncation, archived-item handling, and inaccessible/redacted content. If a bound is exhausted before collection finishes, report partial and ask before broadening. Empty, null, missing, `REDACTED`, or inaccessible results do not establish deletion. Exclude pull requests from repository Issue lists when publishing stories; distinguish Issues, PRs, drafts, and redacted Project items. Never treat a filtered UI view as the whole Project.

## Exact approval and durable records

Follow COMMON's explicit destination/retention rules. Drafts may stay chat-only. Before any mutation, resolve an approved **durable run folder** and collision-safe manifest/results paths, not an assumed temp/current-directory location. Save an immutable approved manifest; save attempts and resolved bindings separately. Retain for recovery; cleanup requires exact-path authorization. [Run record template](../skills/github-operations/run-records.md) defines library-owned semantics, not API fields.

Review exact targets, operations, title/body/format/metadata/links/markers, payloads or complete templates and hashes, source hashes/baselines, dependencies, exclusions, verification, retry bounds, and residual risks. Approval of local stories is not publication approval. One approval covers an unchanged exact batch; material changes require a new approved manifest version, never in-place edits.

**Publication privacy gate:** verify repository and Project visibility before approval and again before publication. Review title, raw body (including hidden HTML comments), labels/metadata, references, links, source paths, and recovery markers for secrets, personal/internal information, and unauthorized disclosures. Public repository Issues are public even on a private Project. A public Project does **not** grant access to private-repository Issues; do not promise a public demo can show them. Project metadata may itself be public. Unknown visibility/authority blocks publication; never change visibility to fix it. Require explicit confirmation of the exact public content/destinations when either destination is public. Issue creation can trigger notifications.

### Approved dependencies and placeholders

Creating an Issue, adding it to a Project, and setting Status are separate operations/calls. An immutable manifest may approve typed placeholders for the Issue node ID returned by its exact create operation and the Project-item node ID returned by its exact add operation. Specify prerequisite operation key, transport response property, expected object type/scope, and permitted insertion location. Approve complete payload templates/hashes and target field/option IDs in advance; placeholders cannot defer content, destination, option selection, or privacy decisions.

Bind only verified outputs of those prerequisites. Record resolved values, provenance, payload/hash and validation durably **before** dependent requests; keep original templates unchanged. Missing or ambiguous bindings stop the boundary. Otherwise obtain separate approval after IDs resolve. For a new item's Status, approve an exact permitted initial baseline (e.g., unset) or require separate post-add review; workflows may set a value on add. Do not assume unset.

## Execution, concurrency, and recovery

1. Recheck manifest/source hashes, identity, access, visibility, target IDs, and relevant baseline immediately before each write. Record attempt start durably; persist sanitized response/IDs and verification before dependents. Use a single checkpoint writer or serialized durable updates; stop if recoverable recording fails.
2. Project field updates have **no compare-and-swap guarantee in this MVP**. Narrowly re-read exact item membership, field/type/options, and old Status immediately before update. This is an optimistic check with a residual read/write race, not a lock or conditional write; timestamps and `clientMutationId` are not CAS or deduplication guarantees. Require explicit approval accepting this race, or block if atomic conflict prevention is required. A mismatch stops for rebase review/new approval. Automation can change Status after a write; do not disable it or fight it with retries.
3. Re-fetch and compare exact Issue content/metadata and scope, Project membership/content identity, or selected Status field/option after each respective action. Around Project addition, approve and immediately recheck protected Issue baselines (state, title/body, labels where scoped) and expected permitted initial/relevant Project field values; re-read them after addition as well as membership. Surface known automation effects before approval; effects outside this MVP block that operation pending a separately scoped decision. An unexpected protected-value change is a discrepancy: retain the observed membership outcome and stop dependent mutations for review, without asserting causality, reverting, disabling automation, or treating membership alone as full verification. A returned ID or HTTP success is insufficient. Record protected observed values, discrepancies, and verification time; do not claim a transactional snapshot of all unrelated data.
4. A timeout/connection loss after create is **uncertain**, not a failed create. Never blindly retry. Use checkpointed IDs first; otherwise reconcile within approved repository/run bounds, including open and closed Issues, using the approved stable source/operation marker plus exact material and author/time/scope evidence. Title alone never proves identity. Hidden markers are publicly retrievable body content, not private storage. Without an approved discoverable marker/recovery method, stop for user reconciliation rather than silently injecting one.
5. One exact candidate can be recovered after verification; multiple candidates stop. Zero candidates under incomplete visibility, pagination, indexing delay, or eventual consistency do not prove absence. Prefer bounded complete repository reads over search-only absence; wait/recheck within approved bounds or request review before an expressly approved bounded retry. Do not broaden reads silently.
6. For uncertain Project add, reconcile exact Project + Issue node identity/membership. GitHub documents that adding an existing item returns its existing item ID; still verify and checkpoint membership, rather than assuming an uncertain outcome. For uncertain Status, re-read: intended value means observed/recovered outcome (not proof who set it); old or different values require conflict review before another write.
7. Resume from immutable manifest + durable attempt history; reverify terminal outcomes before skipping. Preserve operation/source keys and approval lineage. Stop dependent actions on failure; independent continuation must be explicitly planned. No automatic delete/archive/rollback. A created Issue with failed Project add is partial, not permission to recreate it.

## MVP boundary and report

Only reviewed story-to-repository-Issue creation, adding verified existing/new Issues to a selected existing Project, bounded reads, and approved exact single-select Status assignments are supported. Optional initial labels must already exist and be approved; omit by default and verify they were not silently dropped. No full sync, Issue text updates, comments, assignments, estimates, hierarchy/dependencies automation, Issue state changes, Project/field/option creation, visibility changes, archive/delete, or automatic local migration.

Report per-operation proposed/attempted/verified/partial/blocked/uncertain outcomes, separate identity tuples, expected/actual discrepancies, completeness, retained exact paths/actions and remaining decisions. Optional local mapping writeback needs its own approved existing-schema diff and unchanged source baseline; remote success survives writeback failure and must not trigger another create.
